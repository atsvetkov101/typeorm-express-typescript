# Инварианты проекта: что нельзя менять и почему

Документ фиксирует решения, которые нельзя менять произвольно: на них завязаны контракт API, данные, тесты, Docker-окружения и инструменты качества. Если задача действительно требует отступить от инварианта, это нужно согласовать с человеком, описать причину в задаче (раздел «Ограничения и вне рамок»), обновить этот документ и вместе с изменением обновить миграции, тесты и документацию.

Порядок приоритетов при конфликте требований:

1. `docs/ai/GUARDRAILS.md` (этот файл) — жёсткие инварианты.
2. Конфиги `tsconfig.json`, `.eslintrc.js`, `.prettierrc`, `.commitlintrc.ts`, `.lintstagedrc` — источник истины по стилю и проверкам.
3. `docs/ai/STYLEGUIDE.md`, `docs/ai/DEFINITION_OF_DONE.md` — как писать код и когда задача считается готовой.
4. `AGENTS.md` — процесс работы агента.

## 1. Контракт API и обработка ошибок

| Нельзя менять                                                                                                                    | Почему                                                                                  |
| -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Формат успешного ответа `{ message, data }` и сигнатуру `res.customSuccess(status, message, data?)` (`data` по умолчанию `null`) | На нём построены все контроллеры, тесты, Postman-коллекция и внешние клиенты            |
| Формат ошибки `CustomError.JSON`: `errorType`, `errorMessage`, `errors`, `errorRaw`, `errorsValidation`, `stack`                 | Его напрямую отдаёт `errorHandler`, поля проверяются в тестах                           |
| `errorHandler` как последний middleware в `src/index.ts`                                                                         | Иначе `CustomError` не превратится в JSON-ответ и упадёт в дефолтный обработчик Express |
| `getLanguage` до подключения роутов                                                                                              | Контроллеры и middleware рассчитывают, что `req.language` уже установлен                |
| Запрет на `res.status(...).json(...)` и `throw` в контроллерах                                                                   | Ломает единый формат ошибок и централизованную обработку                                |
| Набор кодов: `200` — успех, `400` — валидация/общая ошибка, `401` — JWT/права, `404` — не найдено, `409` — конфликт сохранения   | Коды зафиксированы в тестах и клиентах                                                  |

Вместо изменения контракта: расширяйте `data` обратно совместимо и добавляйте новые поля, не удаляя существующие.

## 2. Схема БД и TypeORM

| Нельзя менять                                                                                             | Почему                                                                                                   |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `synchronize: false` в `src/orm/config/ormconfig.ts` — нельзя включать даже временно                      | Автосинхронизация меняет схему в обход истории миграций: риск потери данных и расхождения dev/stage/prod |
| `SnakeNamingStrategy`                                                                                     | Все колонки в БД в `snake_case`; без стратегии TypeORM начнёт искать `createdAt` вместо `created_at`     |
| Уже применённые миграции нельзя редактировать, удалять и переименовывать                                  | В таблице `migrations` хранится имя и timestamp; на stage/prod они уже применены — правка ломает историю |
| Формат миграций: файл `<timestamp>-<Name>.ts`, класс `Name<timestamp>` с полем `name`, методы `up`/`down` | По этому формату работает TypeORM CLI                                                                    |
| `getRepository` / `dbCreateConnection` как способ доступа к БД                                            | Прямые `createConnection`/`getConnection` в контроллерах ломают единое подключение и тесты               |
| Сиды только как демо-данные (отдельный конфиг `ormconfig-seed.ts`)                                        | Сиды не должны содержать бизнес-логику и выполняются в контейнере при старте                             |

Изменение схемы: только новая миграция через `npm run migration:generate` / `migration:create`, затем `migration:run:dev`.

## 3. Архитектура и точки входа

| Нельзя менять                                                      | Почему                                                                                                                   |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `src/index.ts` экспортирует `app`                                  | Тесты импортируют `import { app } from '../../'`; перенос/переименование сломает их                                      |
| Слои `routes → controllers → middleware → orm`                     | На разделении слоёв построены соглашения проекта; бизнес-логика в роутах или валидация в контроллерах размывают контракт |
| Префикс `/v1` в `src/routes/index.ts`                              | Публичный контракт API и Postman-коллекция                                                                               |
| Абсолютные импорты от `src` (`baseUrl: "src/"`, `NODE_PATH=./src`) | Работает одновременно в `dev`, `start`, тестах, миграциях и сидах; массовый переход на относительные пути хрупок         |

## 4. Безопасность и аутентификация

| Нельзя менять                                                                                       | Почему                                                                                 |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Хеширование только через `User.hashPassword()` и проверку через `checkIfPasswordMatch()` (bcryptjs) | Единая политика хранения паролей; ручной хеш/сравнение легко сделать небезопасным      |
| Секреты JWT только из `JWT_SECRET` / `JWT_EXPIRATION`                                               | Хардкод секретов недопустим; значения различаются по окружениям                        |
| `checkJwt` и `checkRole` на защищённых роутах, порядок middleware                                   | Ослабление открывает доступ к чужим ресурсам и админским операциям                     |
| Значения ролей `ADMINISTRATOR` / `STANDARD` и языков `en-US` / `ru-RU`                              | Строковые union-типы и данные в БД; смена значений требует миграции данных             |
| `cors`, `helmet`, `body-parser` в `src/index.ts`                                                    | Базовые настройки безопасности и разбора запросов; отключение — только осознанно       |
| Пароли, токены и реальные секреты не коммитятся в `config/*.env`                                    | `.env` в репозитории — демонстрационный; prod/stage-значения секретов хранятся вне Git |

## 5. Конфигурация и окружение

| Нельзя менять                                                                                                                                  | Почему                                                                                                         |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Имена переменных `PORT`, `NODE_ENV`, `PG_HOST`, `PG_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `JWT_SECRET`, `JWT_EXPIRATION` | Они используются в `ormconfig`, `docker-compose*.yml`, npm-скриптах, `ProcessEnv.d.ts` и `.vscode/launch.json` |
| `PG_HOST=localhost` в `migration:run:dev`, `migration:revert`, `migration:generate`, `seed:run:dev`                                            | Локальный запуск идёт мимо Docker-сети; в контейнере используется `PG_HOST=db_boilerplate`                     |
| `import 'dotenv/config'` в начале `src/index.ts`                                                                                               | Без него не читается `.env` и приложение не стартует локально                                                  |
| Отсутствие новых env-переменных в `ProcessEnv.d.ts`                                                                                            | TypeScript не увидит свойство, а окружения разойдутся                                                          |

Новую переменную добавляйте сразу в `.env`, `config/*.env`, `src/types/ProcessEnv.d.ts` и, если нужно, в `docker-compose*.yml`.

## 6. Инструменты качества и процесс

| Нельзя менять                                                                                                      | Почему                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `.eslintrc.js`, `.prettierrc`, `tsconfig.json`, `.lintstagedrc`, `.commitlintrc.ts`, Husky-хуки — нельзя ослаблять | На них завязаны `lint-staged`, проверки перед коммитом и единый стиль                                                |
| `npm run lint` = `eslint --max-warnings 0` + `tsc --noEmit`                                                        | Ноль предупреждений — обязательное условие; ослабление пропустит ошибки                                              |
| `noImplicitReturns`, `noFallthroughCasesInSwitch`, `experimentalDecorators`, `emitDecoratorMetadata`, `typeRoots`  | Нужны для строгости и работы декораторов TypeORM/ambient-типов                                                       |
| `@typescript-eslint/no-explicit-any: error` и `noImplicitAny: true`                                                | Запрещают явный и неявный `any`; ослабление скрывает ошибки типов и пропускает небезопасный код через `npm run lint` |
| Запрет `Array.reduce` (`eslint-plugin-no-array-reduce`) и правило `import/order`                                   | Зафиксировано в ESLint и STYLEGUIDE                                                                                  |
| Conventional Commits                                                                                               | Commitlint и Husky блокируют коммиты другого формата                                                                 |

## 7. Скрипты `package.json`

Существующие имена скриптов (`dev`, `build`, `start`, `lint`, `lint-fix`, `tsc`, `format-fix`, `test`, `commit`, `docker:*`, `migration:*`, `seed:*`) переименовывать нельзя: на них ссылаются `AGENTS.md`, `scripts/be-node-dev.sh`, Docker-образ и документация. Новые скрипты добавлять можно.

## 8. Docker и инфраструктура

| Нельзя менять                                                                                | Почему                                                                                             |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Имена сервисов/контейнеров `be_boilerplate`, `db_postgres`, `container_name: db_boilerplate` | На `db_boilerplate` завязан `PG_HOST` в `.env`; на имена — команды `docker-compose` в документации |
| Порты `5432` (PostgreSQL) и `4000` (API)                                                     | Совпадают с `.env`, `docker-compose*.yml`, `AGENTS.md` и `launch.json`                             |
| Порядок в `scripts/be-node-dev.sh`: `wait-for-it` → `migration:run` → `seed:run` → `dev`     | Схема и данные должны быть готовы до старта приложения                                             |
| `env_file: .env` и volume `./database/boilerplate`                                           | Иначе контейнер не получит настройки, а данные БД не сохранятся между перезапусками                |

## 9. Демо-данные и тесты

| Нельзя менять                                                               | Почему                                                                                                        |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Демо-учётки `admin@admin.com` / `pass1` и `standard@standard.com` / `pass1` | Используются в `AGENTS.md`, примерах `curl`, Postman и ручных проверках; менять только вместе с документацией |
| Фреймворк тестов: Mocha + Chai + Supertest, файлы `*.test.ts` рядом с кодом | Зафиксировано в `package.json` и STYLEGUIDE; тесты импортируют `app` и работают с реальным PostgreSQL         |
| Тесты выполняются на реальной БД (`dbCreateConnection`), без моков БД       | Это принятая модель интеграционных тестов; замена требует отдельного решения                                  |
| Уникальность `email`/`username` в тестовых данных                           | Ограничения БД: дубликаты уронят `beforeEach`                                                                 |

## 10. Документация для агентов

| Нельзя менять                                                                                                                                                              | Почему                                                                |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| Роли файлов: `AGENTS.md` — точка входа, `PROMTS.md` — журнал промтов (новые сверху), `docs/ai/*` — контекст/стиль/DoD/инварианты, `tasks/TASK_TEMPLATE.md` — шаблон задачи | На них ссылаются агент и процесс работы                               |
| Язык: документация для агентов — русский, код/идентификаторы/сообщения API — английский                                                                                    | Зафиксировано в STYLEGUIDE                                            |
| Ссылки между документами                                                                                                                                                   | Переименование/удаление без обновления ссылок ломает навигацию агента |

## 11. Что можно менять свободно

- Добавлять новые роуты, контроллеры, middleware/валидаторы, сущности, миграции, сиды, тесты и утилиты по существующим слоям.
- Расширять успешные ответы новыми полями в `data` (обратно совместимо).
- Добавлять env-переменные с обновлением всех перечисленных выше мест.
- Обновлять документацию и примеры, если изменение поведения согласовано.

## 12. Если отступить от инварианта всё-таки нужно

1. Согласовать изменение с человеком и зафиксировать причину.
2. Описать отступление в задаче в разделе «Ограничения и вне рамок».
3. Обновить этот файл (`docs/ai/GUARDRAILS.md`) и затронутые документы.
4. Добавить миграцию данных/схемы, обновить тесты.
5. Прогнать `npm run tsc`, `npm run lint`, `npm test`, `npm run build`.
